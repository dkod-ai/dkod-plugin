# Migrate an app DKOD did not build

The original app and its data are read only: you read them, you never change them, and you never install into it or generate anything in it (lock file, dependencies folder, build output). The snapshot copies only the store the original already reads (its .env/.env.local URL, its running process, or the `--db-url` the builder gives): never create a data store for the original and never run its seed, fixtures, `db push`, `migrate reset` or migrations to get data; when no store is reachable, ask the builder for the URL. A CSV or JSON data file the original reads (named by its .env, by its code, or under a `data/` folder) is data too: the snapshot copies it, and the import reads it. The dk- app is a new app, built in the `folder` that `dkoder.migrate.start` returns.

Call `dkoder.migrate.start` first, with the `sessionId` and the app key: the original folder's own name as the dkod skill defines the key (a folder `aisf-test-dko1411-x` gives `aisf-test-dko1411-x`; a different name in the request is not used). The dk- app's key is `dk-<that key>` (`dk-aisf-test-dko1411-x`). Take `migration`, `folder`, `templates` and `steps` from its answer. What the app is built on, and with which template, comes from that answer and from the dkod skill. This file says only the order of the steps: never pick a template yourself.

Parity is checked here, on this computer, before any deploy: the original and the dk- app both run on `localhost`, and the frozen suite runs on each with `PARITY_BASE_URL=http://localhost:<port>`. Never point the parity suite or a browser at a prod URL: prod sits behind the organization's sign-in gateway. Deploy and the code upload stay held until the builder confirms parity. After that, Deploy only waits until the dk- app is healthy; nothing checks parity on prod. A step out of order is refused and nothing moves.

## The steps, in order

### 1. Start

Make the `folder` the call returned, beside the original app's folder. Write `<folder>/.dkod/migration.json` with exactly two fields: `original`, the original folder's absolute path, and `appKey`, the original's app key (the original folder's name, not a name from the request). Calling start again on the same app starts the attempt over and clears every fact reported so far. Take `service_rules` from the call too: one rule per policy of `migration.cache`, `migration.blob` and `migration.external_services`, which steps 2, 3, 4 and 5 apply.

### 2. Map the original

Map the original app so completely that the dk- app can be built from the map and the parity suite alone. The map lives in `<folder>/.dkod/map/` and stays on this computer.

First make the original's code graph, outside the original: run `node <scripts>/dkod-graph.mjs ensure <the original's folder> --out <folder>/.dkod/map/graph`, as the dkod skill's "Code graph" section says (`<scripts>` is the dkod skill's `scripts` folder). It writes nothing in the original. Map the original by asking that graph through the script (`node <scripts>/dkod-graph.mjs query`, `explain` and `path`, with `<folder>/.dkod/map/graph/graphify-out/graph.json` as the graph), and start from its GRAPH_REPORT.md: routes, pages, stores, services, functions and how they connect. Open an original file only where the graph points. Build the dk- app the same way: run `node <scripts>/dkod-graph.mjs ensure <folder>` once the dk- app has code, and again after large changes. When the graph cannot be made, the dkod skill says what to tell the builder; map the original without it.

1. Take the data snapshot first (step 3's `<scripts>/dkod-migrate.mjs` snapshot <folder>; it copies single-file stores and CSV/JSON data files, and prints `mode` `snapshot` for them, not `new-app-only`), and run the original on that scratch data, never on its own. The original stays read only, on its own store, never one you made: to run it, take screenshots or read computed styles, copy it without `.git` to the run's scratch folder (one `mktemp -d` folder per run, or the scratch folder `snapshot` or `start` prints; never a fixed /tmp/<name>, which other users of this computer may own; the output of your own commands goes there too: `curl -o`, `wget -O`, saved answers, notes, logs), install its dependencies there with the package manager the dkod skill names for its stack, run the copy on the snapshot's scratch data from its production build and start, never a dev server (Next.js: `next build`, then `next start`), and delete the copy when the map is done. Run every command that installs or starts the copy with `TMPDIR=<that scratch folder>` and `PIP_CACHE_DIR=<that scratch folder>/pip-cache`, and prefer a venv interpreter or `python3 -I` over the bare /usr/bin/python3 shim, as the dkod skill's scratch-files rule says. Run `git status --short` in the original before the map and again at the end of this step: it must print nothing new.
2. Write `<folder>/.dkod/map/app-map.json` in the app map shape: `summary`, `routes`, `stores`, `services`, `settings`, `background`, `local_only`, `flows` and `pages`, with the enums of the `dkoder.migrate.report` schema. List every route, page and service, with no count cap; the report keeps a bounded preview. A setting is a NAME, never a value; the KEY names of `.env`, `.env.example` and `.env.*` files count as settings. `services` lists every outbound host and SDK client the code uses; a service name may hold several, such as `api.stripe.com, stripe`, and covers each one it contains. Add `tables`, a list of `{ store, name, columns }`, for every table (CREATE TABLE in .sql or code, a CSV under `data/`) and its columns. Add `queries`, a list of the exact SQL strings as written in the code; `functions`, a list of function names; and `design`, `{ colors, fonts, buttons, tooltips }`: `colors` are lowercase hex colours of the original's css, `fonts` the font-family value as written (the whole stack), or each non-generic family of it, `buttons` the id and `name=` value of each button, `tooltips` the `data-tooltip-id`, `data-tip-id`, `data-tooltip` and `aria-describedby` values and the `tip-*` ids (an id listed in either covers it). These stay on this computer.
3. Visit every page and every state of it with a headless browser (Playwright, run through `bunx`): `default`, `empty`, `loading`, `error`, `signed_out`, and each tooltip, dialog, menu, hover and focus state. For each, save a screenshot and the computed styles (colours, fonts, sizes, spacing) to `.dkod/map/design/pages/<slug>/<state>.png` and `<state>.json`. The `<slug>` is the page path in lower case with every run of other characters as `-`; `/` is `home`. A page without a `default.png` fails the check. Capture only the original's production build and start, never a dev server: record in each state's `.json` a `dev_overlay` list naming the framework overlay elements found, such as `["nextjs-portal", "nextjs-dev-indicator"]`, or an empty list. check-map and freeze refuse a state whose json lists any.
4. List the original's css, fonts, icons and images in `.dkod/map/assets/assets.json` as `[{ "kind": "css|font|icon|image", "path": "<path in the original>" }]`, and copy the files into `.dkod/map/assets/`.
5. Run `<scripts>/dkod-migrate.mjs` check-map <folder> `--original-url http://localhost:<port>` whenever the original runs on scratch data: it asks the running original what it serves and lists the pages, GET routes, colours, fonts, button and tooltip ids the map misses (`missing_pages_runtime`, `missing_routes`, `missing_colors`, `missing_fonts`, `missing_buttons`). Without the URL it prints `runtime: not checked` and is not ok, unless the map gives the reason the original cannot run in `original_cannot_run`. It checks the map against the app map shape, lists the routes it finds in the original's router files that the map misses (`missing_routes`), the pages without a screenshot (`pages_without_screenshot`), and the tables, columns, settings, colours (in stylesheets and code), functions, SQL queries, font families, button and tooltip ids, and outbound hosts and SDK clients of the original that the map misses (`missing_tables`, `missing_columns`, `missing_settings`, `missing_colors`, `missing_functions`, `missing_queries`, `missing_fonts`, `missing_buttons`, `missing_services`; a query longer than 200 characters is printed as a `q:` id that goes into `queries` or a `not_mapped` name as is). It also prints `missing_count` (the total and the count per kind), refuses stand-in page renders (`placeholder_screenshots`: one image shared by 3 or more pages, or by every page), and refuses `original_cannot_run` while a local server the original needs (by its stores and dependencies) is installed on this computer (start it and run the original). An item that is truly not an omission leaves its list only through a `not_mapped` entry `{kind, name, why}` in the map (counted in `justified`; an entry that matches nothing is a problem). Fix what it names and run it again until it prints `"ok":true`.
6. For each redis/kv store, each blob/file store and each `services` entry of the map, note the policy in `service_rules` (`migration.external_services.hosts` over its `default`). On `refuse`, stop: tell the builder to have an admin change migration.yaml on the Control page, and go on only after a new start call returns another policy.
7. Call `dkoder.migrate.report` with the `sessionId`, the app key, step `mapped`, and `map`: send only names and counts, never a file, a value or a screenshot.

### 3. Write the parity suite

Write a Playwright suite in `<folder>/tests/parity/` from the map, and get every test to pass on the original before you write a line of the dk- app. Tag every test in its title, so `freeze` can check the suite against the map:

- `@api METHOD /path`: one per `api` route of the map (the API kind: status and response shape).
- `@page /path`: one per page route and page of the map (the end-to-end kind: the page renders and its main actions work).
- `@flow <name>`: one per flow of the map, named as the map names it (end-to-end).
- `@data`: write, read back, restart the app, read again. Needed when the map has stores (the data kind). Freeze refuses an `@data` test whose body has no restart between the write and the second read. Restart with the shipped helper: run `<scripts>/dkod-migrate.mjs` install-restart <folder> before the suite (it writes `tests/parity/restart.ts`, part of the frozen suite), `import { restartApp } from "./restart"` in the test, and set `PARITY_START_CMD` (the command that starts the app), `PARITY_START_CWD` and `PARITY_RUN_DIR` (the run's `mktemp -d` folder) in every run, and `PARITY_START_ENV` (env files, a path relative to `PARITY_START_CWD` or absolute, several separated by `:`) for each side: the original's run points to `<scratch>/.dkod-snapshot.env`, the file `snapshot` writes with the values it printed (`DATABASE_URL` of the copy, the file keys), never to the original's own `.env`/`.env.local`, so the restarted original stays on the copy; the dk- app's run points to the dk- app's `.env` (Dev `DATABASE_URL`, no `REDIS_URL`). The restarted app sees only `PATH`, `HOME`, `PORT`, `TMPDIR`, `LANG`, `SHELL`, `PIP_CACHE_DIR`, the `PARITY_*` names and that file's variables, no other variable of the runner; the runner's `PORT` and `PARITY_*` win over the file. `restartApp()` stops the app on `PARITY_BASE_URL`'s port, starts it again as a child of the run and records its PID and port in the run folder. Never write a restart of your own with `setsid`, `nohup`, `disown`, `detached: true` or `unref()`: freeze refuses it.
- `@design /path <state>`: one per page state that has a screenshot in `.dkod/map/design`, with `toHaveScreenshot("<slug>-<state>.png")` and the baseline copied from `.dkod/map/design/pages/<slug>/<state>.png` to `tests/parity/__baselines__/<slug>-<state>.png` (the design kind). The dk- app's `parity` project reads baselines from that folder with that name (`snapshotPathTemplate: "{testDir}/__baselines__/{arg}{ext}"`).

The suite reads only `PARITY_BASE_URL` to pick the app, so the same files run on the original and on the dk- app unchanged. Run it on a copy of the original's data, never on its own: run `<scripts>/dkod-migrate.mjs` snapshot <folder>, the way the dkod skill runs its own scripts (add `--db-url <url>`, or `--original-url http://localhost:<port>` with the original running, when it reads its data URL from its environment and no .env names it; never write `.dkod/snapshot.json` by hand, `check-build` refuses it; snapshot refuses a source named `*_dkod_migrate`, a scratch name or a store created in the last 10 minutes, and `snapshot.json`'s `source` names the store it copied, on the original's own store, never one you made), and start the original with the values its answer printed, from its production build and start, never a dev server (Next.js: `next build`, then `next start`). The dk- app does not exist yet, so write `tests/parity/playwright.config.ts` first: one project `parity` with `testDir: "."`, `snapshotPathTemplate: "{testDir}/__baselines__/{arg}{ext}"`, `use.baseURL` from `PARITY_BASE_URL`, and `expect.toHaveScreenshot.maxDiffPixelRatio` from `PARITY_MAX_DIFF_RATIO` (the `parity.visual_max_diff_ratio` of the migration file; set that variable in every run here; when it is not the default 0.001, also put `PARITY_MAX_DIFF_RATIO=<the ratio>` before `playwright test` in the app's `parity` script). The sha256 covers `tests/parity` only, so this file is part of the frozen suite and nothing outside the folder is. Before you write the suite, write the dk- folder's `package.json` for the stack's package manager and add `@playwright/test` as a devDependency at the folder root (for example `<manager> add -d @playwright/test`). Never put a `package.json`, a lockfile or `node_modules` in `tests/parity`: `freeze` refuses them, and once frozen Dkoder refuses an install run in or naming that folder. Run the suite, and start the original for it, with `TMPDIR=<the scratch folder>` and `PIP_CACHE_DIR=<the scratch folder>/pip-cache` (the dkod skill's scratch-files rule), preferring a venv interpreter or `python3 -I`. Run the suite with the manager's runner, `PARITY_BASE_URL=<the original's url> PARITY_MAX_DIFF_RATIO=<the ratio> <runner> playwright test -c tests/parity/playwright.config.ts --reporter=json > <a file outside .dkod>`, where `<runner>` is the manager's own (`<manager> exec`, `<manager>x` and so on), for example in the run's scratch folder (`mktemp -d`, never a fixed /tmp/<name>: other users of this computer may own it; the capture script, the policy pack and the suite reports all stay there, or in the scratch folder `snapshot` prints). Save the reporter's output exactly as it prints and never write a report file by hand: `freeze`, `check-build` and `side-by-side` refuse a summary (specs with `ok` and nothing else) that lacks the reporter's `config`, `stats` and `suites`.

When a test fails on the original, `freeze` lists it as an original failure. With `original_failures: ask` (the default of the migration file), show the builder each failing title and ask: fix the test, or drop it. Drop means you remove the test and say so in your reply to the builder. Run the suite again after every change.

Run `<scripts>/dkod-migrate.mjs` snapshot <folder> before the suite runs: it records the per-table row counts and md5 hashes of the scratch data, and keeps a second untouched copy (the base) that only the import reads. Then run `<scripts>/dkod-migrate.mjs` freeze <folder> <that report file>. It prints a coverage report; it also writes the scratch data identity (`data.tables`) and the tables the suite itself wrote to (`data.suite_writes`) into `freeze.json`, and exits 1 when the scratch tallies are missing or unreadable: run snapshot again and rerun the suite. With a gap (`missing`) or a failure it exits 1 and writes nothing: fix it and run it again. When it prints `"ok":true` it has written `.dkod/parity/freeze.json` and printed `sha256` and `counts`. Report step `tests_green_on_original` with `suite_sha256` set to that `sha256` and `counts` set to that `counts` (`tests`, `original_passed`, `original_failed`). It is the one the parity step runs again. Never compute it by hand.

After the freeze, never edit `tests/parity`: Dkoder refuses it. To change the suite, run `<scripts>/dkod-migrate.mjs` unfreeze <folder> and start the attempt again with `dkoder.migrate.start`, because a changed suite has a new sha256 the server does not match.

### 4. Build the dk- app

Build the dk- app in the `folder`, on the stack and on the template the start call returned. Report step `building` when this step starts. The map and the frozen suite are the spec; the original's code is not. Never serve the original's rendered HTML, build output or screenshots; every page is rebuilt on the stack.

1. Render the template: the one that `dkoder.templates` named in the start call. Never pick another. Save its `content` to a file outside the dk- folder (the run's scratch folder from `mktemp -d`, or the one `snapshot` prints; never a fixed /tmp/<name>, which other users of this computer may own), and its `dkod` values and `policy` values to a `values.json` beside it (`{ "policy": {...}, "dkod": {...} }`). Run `<scripts>/dkod-migrate.mjs` render <that template file> <folder> <values.json>. It writes the Dockerfile, CI, package.json and the other files DKOD puts in the repository, with every placeholder answered, and never overwrites a file that exists unless you add `--force`. It exits 1 and writes nothing on an unanswered placeholder (`gaps`): answer it in `values.json` and run it again. Then build on the rendered files. Never copy the template's text into the folder: its `{{#if ...}}` branches are not a Dockerfile.
2. Copy the files listed in `.dkod/map/assets/assets.json` from the original as they are, into the places the template serves them from. Never redraw one: `check-build` compares the bytes.
3. Write every route, page, API path and flow of the map, so the frozen suite can pass on the dk- app.
4. Write the data layer the stack names: a schema from the map's `tables`, and a `0001_baseline` migration made from it. The original's data files, and any driver for them, stay out of the `folder`.
5. Give the app its Dev data: do the dkod skill's section on Dev data. Call `dkoder.devdb.status`, and `dkoder.devdb.make` when it asks for it; the Dev data belongs to the original app's key, the `appKey` in `.dkod/migration.json`: pass that key to `dkoder.devdb.status`, `dkoder.devdb.make` and `dkod-db.mjs` (`--app <that key>`), never a `dk-` name, so the app has one set of Dev data. Run `dkod-db.mjs` up so it writes `DATABASE_URL` into `.env.local` (in Cursor, or any agent with no background tool, the one command `node "<scripts>/dkod-db.mjs" up --app <app key> --detach`, run as the dkod skill says (no `&&`): it returns once the Dev data answers and leaves the tunnel running; `node "<scripts>/dkod-db.mjs" down --dir <folder>` stops it, and you run it for each folder that started a tunnel at the end of the run, after parity and deploy, and on every stop); then run `dkod-db.mjs` migrate. `.env.local` must be in `.gitignore`, and you never read or print its values.
6. Read `data_import` in the migration file. With `ask`, ask the builder whether to bring the original's data (with the question tool; if it is not available, stop, ask in plain text and wait for the reply, and never pick an answer yourself). On a yes, make sure `<scripts>/dkod-db.mjs up --app <key>` runs in the background (in Cursor: `node "<scripts>/dkod-db.mjs" up --app <key> --detach`), run the app's `db:migrate`, then run `<scripts>/dkod-db.mjs import --app <key> --from snapshot --dir <folder>`. It copies every mapped table from the snapshot's untouched base copy (a second copy of the dump that `snapshot` makes and the original and the suite never run on; for an original whose data is in a data file, the untouched copy of each data file that `snapshot` keeps: a single-file store read with the `sqlite3` command, a CSV or JSON data file read as rows of its mapped table) into the Dev store, so Dev gets the original's data as it was before the original ran, never rows the original or the suite wrote in foreign-key order, in one transaction, and prints the per-table row counts and md5 hashes for the original and for Dev, never a row value. Warn the builder once that Dev is shared by every builder in the org and keeps 1 day of backups. Show the builder the per-table counts. The import refuses a `--from` source that is not the data the suite was frozen on (exit 1, Dev untouched, the tables named) and exits 2 when there is no `freeze.json` or when `snapshot.json` has no base copy (run snapshot again, rerun the suite and freeze again): never change the scratch data after the suite ran. On exit 1 stop and show the printed sentence and the table report (a hash mismatch, which rolls Dev back, a Dev table whose rows differ from the original's, or a read error). A Dev table whose rows differ means the dk- app's own migrations insert rows that differ from the original's: change those migrations to insert exactly the original's rows (or none), drop and remake Dev, run `db:migrate` and import again, and never delete or edit Dev rows by hand; `check-build` fails on the same thing by running the migrations on a fresh empty store. On success `snapshot.json` gets `imported: true`, so `data_imported` is true; a table `db:migrate` already filled with the same rows as the original is skipped and listed in `already_present`; show the builder any `skipped_tables` and `dropped_columns` (names only) the output lists. On exit 2 first tell the builder the printed sentence (why the data was not imported), then follow it: fix the cause (Dev not up, `DATABASE_URL` missing, `db:migrate` not run, `sqlite3` not installed) and run the import again; only when it says the original's data is not in a local store the import can read, or that it cannot be imported, go on with an empty, migrated Dev store, and only after the builder has been told. Invent no other import command. After a Yes, never hand-write a seed or insert rows in place of the import, for a CSV/JSON data file as for any other store; when the import exits 2 for a data file (no mapped table, wrong shape, no shared column), tell the builder the printed sentence and go on with an empty, migrated Dev store. The rows the suite reads come from a `db:seed` script in the dk- app's package.json: it inserts the original's rows the suite ran green on, idempotently (`insert ... on conflict do nothing`, or skip a table that already has rows), and never deletes, truncates, drops or updates rows (Dev is shared by every builder in the org), and CI runs it after `db:migrate` on an empty data store. Run it on the Dev data only when there was no import: after a successful import Dev already holds the rows, and `db:seed` would fail on primary keys or duplicate them. Never insert rows by hand or with a one-off script: after an import, `check-build` and `side-by-side` re-read Dev and fail with "Dev changed after the import: db:seed or hand-written rows" when a mapped table differs from what was imported (tables the suite itself wrote to are allowed). With `never`, do not ask.
7. Apply each store and service policy: `stub` means an in-process stub with the same interface, seeded from the snapshot, and the service's settings stay unset; `keep` (cache and blob only) keeps the same kind of store on a Dev instance named by setting NAMES only; `public-read-only` allows only GET/HEAD to that public host with no credential, no auth header and no API key. Never give the dk- app a real credential for an external service. Never start a local Redis, `redis-server` or a local file store (`STORAGE_DRIVER=local`) for the dk- app: follow the `migration.yaml` cache and blob policy, `stub` (in-process), `keep` (Dev instance, setting names only) or `refuse` (the app runs without it).
8. Loop until everything passes: start the dk- app on the Dev data, and run the frozen suite on it with `PARITY_BASE_URL=<the dk- app's url>`, `PARITY_MAX_DIFF_RATIO` and `--reporter=json`, writing to a file outside `.dkod`. Then run `<scripts>/dkod-migrate.mjs` check-build <folder> <that report file>, each required check of the template (run its script by name, as the PRD's "Required checks" list them) and the dkod skill's policy checks, the stack rule among them. Fix what any of them names and run all of it again, until the suite is green, `check-build` prints `"ok":true` and no policy finding blocks.

`check-build` fails on a suite edited after the freeze, a baseline test that fails or is missing, a map table with no schema, no `0001_baseline` migration, a data file in the `folder`, an asset that is not byte-identical, a `.env.local` that is not ignored, a `test-results/` or `playwright-report/` folder that `.gitignore` does not ignore, a Dockerfile, workflow, package.json or source file that still has template text (`{{#if`, `{{else}}`, `{{ dkod.`...), a package.json with no lock file, a file outside `tests/parity` that is byte-identical to a design screenshot of the map, the original's build output (a `_next` folder, `webpack-*.js`, a `chunks/` path, a buildManifest), and served HTML that has the original framework's page data, static paths or route announcer (`__NEXT_DATA__`, `/_next/static/`) or is a copy of a page the original rendered, a code or style file outside `tests/parity` that is byte-identical to a code file of the original that `assets.json` does not list (rebuild it on the stack; data files stay allowed), a mapped Dev table that changed after `dkod-db.mjs import` (db:seed or hand-written rows), a db:seed file (named in the db:seed script, `seed*`, or under seeds/ or seeders/) that deletes, truncates or drops rows, an env file, script, compose file or source file that points at or starts a local Redis or file store (`REDIS_URL=redis://127.0.0.1`, `STORAGE_DRIVER=local`, `redis-server`; follow the migration.yaml cache and blob policy), and the policy check's block findings in the folder (a `FROM` pinned by tag fails `pinned-base-images`). Keep its `counts` for step 5.

### 5. Parity

The builder judges parity, not you. Do these in order:

1. Run both apps with every stubbed service's settings unset and pointed at the stub; `public-read-only` hosts get GET/HEAD with no credential only. Never give either app a real credential for an external service. Start the original from the snapshot's values (`.dkod/snapshot.json`, its `env`) on the scratch data, on its own `localhost` port. Start the dk- app on the Dev data, on another `localhost` port. Both run on this computer; nothing is deployed yet. Start each from the run's `mktemp -d` folder and never detach it (no `setsid`, `nohup`, `disown`): record its PID in `<run folder>/pids` and its port in `<run folder>/ports`, one per line (`restartApp()` already does).
2. Run the frozen suite on each app with `PARITY_BASE_URL=http://localhost:<that app's port>` and `--reporter=json`, writing each report to a file outside `.dkod`. Never use a prod URL here.
3. Run `<scripts>/dkod-migrate.mjs` side-by-side <folder> <original report file> <dk report file>. It prints the parity report (routes, flows, tests passed on each app, `visual_diff`, `data_imported`) and the question. It exits 1 on a changed suite, a missing report or a failing test: fix it and run from 2 again. Do not pass `--run-dir` here: items 4 and 6 still need both apps running, and item 7 stops them.
4. Open both urls side by side in the browser.
5. Show the builder the report it printed. Report step `parity_passed` with `parity_sha256` set to the same sha256 you sent as `suite_sha256`, and with its `counts` (`tests`, `original_passed`, `original_failed`, `new_passed`, `new_failed`, `visual_diff`).
6. Ask the builder its `question` with the client's question tool, with the options "Ready to deploy" and "Not yet". If the question tool is not available (for example in print mode), stop, ask the same question in plain text with the two options, and wait for the builder's reply. Never pick an answer yourself.
7. Whatever the answer, stop the servers first: run `<scripts>/dkod-migrate.mjs` stop-servers <folder> `--run-dir <the run folder>`. It kills every recorded server and checks that nothing listens on the parity ports (exit 1 names the port and PID that still holds one: stop it and run it again). Say the servers are stopped only after it prints `"ok":true`. On "Ready to deploy", call `dkoder.migrate.confirm`: it is the only call that moves a migration to `confirmed`. Then go on to the section after this one, Push to prod. On "Not yet", ask what is wrong, fix it, and start step 5 again from 1.

Never confirm for the builder. Call `dkoder.migrate.confirm` only after the builder answered "Ready to deploy" (in the question tool or in text); never pick an answer yourself.

### 6. Push to prod

Only after the builder chose "Ready to deploy" and `dkoder.migrate.confirm` answered. From the dk- folder, push to prod as the dkod skill's "Push to prod" says, with the dk- app's app key. Follow the build with `dkoder.build.status` until it is `delivered` and its `deploy` shows the app is up (there is no separate deploy status tool); that is the whole check. Do not run the parity suite on prod and do not walk its pages: parity was proven on this computer. Then report step `shipped`, and run `<scripts>/dkod-migrate.mjs` clean <folder>: it removes the copy of the original's data and closes the migration, so the original is writable again.

## When a step is refused

The refusal names the state the migration is at and the step it waits for. Nothing moves: do that step, then report it.

Write a JSON or text file that holds quotes, backticks or regexes with the Write tool, never with an inline script or `echo` in the shell. A refusal that says "report this Guard block first" is cleared by calling `dkoder_guard_report` with the object it gives, then retrying, without asking the user.

When the attempt was a mistake, or the app turns out not to need migrating, call `dkoder.migrate.abandon`. The attempt is cancelled, and Deploy and the code upload are open again.

## Cancel a migration

Abandoning does not touch the app's Dev data: the answer says it still exists. Ask the person whether to delete it, with everything in it. If yes, call `dkoder.devdb.delete` with the original `appKey` (the one in `.dkod/migration.json`, never a `dk-` name) and `confirm: true`; without it the tool only says what it would delete. Then call `dkoder.devdb.status`: it says `missing` once the Dev data is gone.
